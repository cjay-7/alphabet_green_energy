# Alphabet Green Energy

A Flutter field-survey app for Alphabet Greens, a clean cookstove distribution
program. Field agents use it to register beneficiaries, record stove
installations, run household surveys, and revisit/verify previously
distributed stoves — all backed by Firebase.

## Platforms

This is one codebase serving two very different purposes:

- **Android** is the real app — this is what field agents install and use
  day to day (beneficiary/survey forms, offline queueing, profile
  management). This is the only platform actively published to the Play
  Store.
- **Web** is *not* the same app. It's a minimal self-service **signup
  kiosk**: `lib/main.dart` detects `kIsWeb` and routes straight to the signup
  screen, bypassing login/dashboard entirely. It exists so new field agents
  can register an account via a shared link without installing the Android
  app first. See [Signup architecture](#signup-architecture) below.

## Tech stack

- **Flutter** (Dart) — UI and app logic, targeting Android + Web.
- **GetX** — state management, dependency injection (`Get.put`/`Get.find`),
  and navigation (`Get.to`/`Get.offAll`) throughout.
- **Firebase**
  - **Auth** — email/password accounts for field agents.
  - **Firestore** — beneficiary, survey, visit, and user profile data.
  - **Storage** — stove/ID/consent photos and profile pictures.
  - **App Check** — enforced on both Android (Play Integrity) and Web
    (reCAPTCHA v3); see [App Check](#app-check--local-development) below,
    since this is the single most common source of "it works for me but not
    for them" bugs in this app.

## Getting started

### Prerequisites

- Flutter SDK (stable channel).
- `android/app/google-services.json` and `lib/firebase_options.dart` — both
  are generated via `flutterfire configure` against the `alphabetgreens`
  Firebase project. If you're regenerating them after any package rename or
  new platform target, re-run `flutterfire configure` rather than
  hand-editing — a stale Android `appId` here was the root cause of a
  previous App Check outage.
- `android/key.properties` (release signing — not committed) if you need to
  build a release AAB.

### Running locally

```bash
flutter pub get

# Android (physical device or emulator)
flutter run -d <device-id>

# Web (the signup kiosk)
flutter run -d chrome
```

## App Check & local development

Every build enforces Firebase App Check (`lib/main.dart`), which blocks
Firebase Auth/Firestore/Storage calls unless the client can prove it's a
genuine build of this app. This is correct for production, but it means
**local dev builds fail App Check by default** unless you register a debug
token — on both platforms, separately:

- **Android**: `main.dart` already switches to `AndroidProvider.debug` when
  `kDebugMode` is true. On first debug run, Logcat prints a debug token and
  a link to register it. Register it via:

  ```bash
  firebase appcheck:debugtokens:create <token> --app <ANDROID_APP_ID> --project alphabetgreens
  ```

- **Web**: there's no `kDebugMode`-gated provider swap for web in the
  Firebase SDK, so `web/index.html` sets a fixed
  `self.FIREBASE_APPCHECK_DEBUG_TOKEN` string when running on
  `localhost`/`127.0.0.1` only (never on the real deployed domain — that
  would let anyone bypass App Check by reading page source). That token is
  already registered against the web app in Firebase Console. If you ever
  need a new one, generate it the same way (`appcheck:debugtokens:create`),
  then update the string in `web/index.html` to match.

Symptoms of an unregistered/stale debug token: Auth/Firestore/Storage calls
fail with `firebase-app-check-token-is-invalid` or, on Android specifically,
`App not registered` — and depending on where the failure happens, it can
look like a completely unrelated bug (a silently-stuck login button, a photo
that "uploads" but never lands in Storage, etc.), since several call sites
here historically swallowed the underlying exception. Check this first.

## Signup architecture

The web build's only job is: collect name/email/password/phone, create a
Firebase Auth account, write a Firestore profile doc keyed by `uid`
(`UserRepository.createUser`), and show a confirmation screen
(`SignUpSuccessScreen`) — there is no Dashboard/Login reachable from web by
design. Validation and error handling live in
`lib/src/features/authentication/screens/signup/`.

### Admin approval gate

Every new signup is created with `ApprovalStatus: "pending"` and cannot read
past a holding screen in the Android app until an admin approves it —
otherwise anyone who finds the signup link could create a working field-agent
account. The flow:

1. `UserRepository.createUser` writes the pending `Users/{uid}` doc.
2. A Firestore-triggered Cloud Function, `notifyAdminsOnSignup`
   (`functions/index.js`), fires on that doc's creation. It generates a
   one-time `ApprovalToken`, stores it on the doc, and emails the admin
   addresses in `functions/.env` (`ADMIN_EMAILS`) an Approve/Deny link pair.
3. Clicking either link hits an HTTPS Cloud Function (`approveSignup` /
   `denySignup`) that checks the token, flips `ApprovalStatus` to
   `"approved"`/`"denied"`, and deletes the token so the link can't be
   replayed. No admin login required — the token in the link is the auth.
4. On the Android side, `AuthenticationRepository._setInitialScreen` checks
   `ApprovalStatus` on every auth-state change and routes anything other than
   `"approved"` to `AccountStatusScreen`
   (`lib/src/features/authentication/screens/account_status/`), which
   streams the doc live so an agent waiting there lands on the Dashboard the
   moment an admin approves them — no app restart needed.
5. `firestore.rules` enforces this server-side too: a client can create its
   own `Users` doc only with `ApprovalStatus: "pending"` and no
   `ApprovalToken`, and can never change either field afterward via a normal
   profile update — only the Cloud Functions (Admin SDK, bypasses rules) can
   change approval state. Without this, any authenticated client could just
   set its own `ApprovalStatus` to `"approved"` directly.

#### Cloud Functions setup (one-time)

```bash
cd functions
npm install

# Gmail App Password for the sender account — https://myaccount.google.com/apppasswords
# (the account's normal login password will not work over SMTP)
firebase functions:secrets:set GMAIL_APP_PASSWORD

# ADMIN_EMAILS / SENDER_EMAIL live in functions/.env (gitignored — copy
# functions/.env.example and fill in real addresses before deploying)

firebase deploy --only firestore:rules
firebase deploy --only functions
```

## Offline support

Beneficiary, survey, and visit submissions made without connectivity are
cached locally (`lib/src/features/FormLocalData/`) and synced to Firestore
the next time the agent opens "Local Storage Data" with a connection — photos
upload to Storage at sync time, not at capture time, in the offline path.

## Building for release

```bash
# Bump the version in pubspec.yaml first (versionCode must increase on every
# Play Console upload, independent of versionName)
flutter build appbundle --release
```

Upload the resulting `build/app/outputs/bundle/release/app-release.aab` to
Play Console. See `PLAY_STORE_LISTING.md`, `PLAY_DATA_SAFETY_NOTES.md`,
`PLAY_CONTENT_RATING_NOTES.md`, and `PRIVACY_POLICY.md` for the store
listing content.

## Security notes

- `firestore.rules` / `storage.rules` require `request.auth != null` on
  every path — there's no per-document ownership check beyond that, so any
  authenticated agent can currently read/write any other agent's data. If
  that needs tightening, scope rules to the creating agent's `uid`.
- Older Firestore `Users` documents from before this app's current schema
  may still contain legacy `Password`/`role` fields from a prior version of
  the signup flow — the current code never writes either field, but
  existing legacy documents should be scrubbed and any affected passwords
  rotated if you find them.
